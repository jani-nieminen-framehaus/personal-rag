# P3.1 runbook — the human part

Code done ≠ P3.1 done. The success criteria need these operator steps:

1. `rag golden generate --n 100` (Ollama must be up; a few minutes).
2. `rag golden review` — accept/edit until ≥50 accepted
   (`rag golden stats` to check; spread across topics).
3. Baseline: `rag eval --golden eval/golden_real.jsonl` (records to eval_runs).
4. `rag eval --sweep --golden eval/golden_real.jsonl` — pick the winner.
5. Optional heavy:
   `rag eval --sweep-chunking --markdown <notes root> --golden eval/golden_real.jsonl`.
   The `--golden` flag is NOT optional here: without it the sweep inherits
   the default `eval/golden_set.jsonl`, which has no `relevant_refs`, and
   section mode then fails on every combination.

   SCOPE CAVEAT: this mode re-ingests **markdown only**, while
   `golden_real.jsonl` is generated from the live index — which also holds
   Zeal docsets, PDFs and EPUBs. Rows referencing those can never match in
   the scratch collections, so they depress every row by the same constant.
   Read the **ranking** across `target_tokens` values; the **absolute**
   recall/MRR numbers are not comparable to a normal `rag eval` run and a
   low figure here is not a regression.
6. Commit the winning knobs to config.yaml with the measured delta in the
   commit message (or record "defaults already optimal").

Between eval runs, `rag refresh` (P3.2) keeps the corpus current on its own —
so the index is no longer fixed between step 3 and any later re-measurement.
Each eval row now records `index_points` for exactly that reason. A
**materially changed corpus is the trigger to re-run step 1 and step 4**:
`rag golden generate` drafts only from material it has not seen, and a sweep
winner picked on the old corpus is a claim about a corpus you no longer have.
